实际线程池归属从实际 ThreadPoolExecutor 实例和 beforeExecute 执行入口建立池 → 工作线程 → 任务的对应关系。使用对象身份和准确的 JavaThread/TID，不用线程名称猜测。
任务切换与历史afterExecute 标记本次任务结束。执行记录在任务开始时保存归属，线程随后换任务或换池不会改写旧记录；当前活动与最近完成明确分开。重复使用的 TID 不套用旧 Java 线程。
提交与执行分开execute/schedule 成功返回后记录提交来源；只有 beforeExecute 的准确绑定标为 execution-confirmed。提交观察、未知或多个池的混合证据不会冒充准确执行归属。
原日志及处理表SAMPLE 增加线程池观察数、工作线程归属数；EXEC 增加 executor 编号、真实池类型、活动/最近完成及对应任务。处理记录的展开执行证据沿用同一份信息；导出仍使用明细页原按钮。

这次核对到的 GIF 停止方式

QQ 9.2.25 的 RenderTask 会调用原生 renderFrame，并再次通过 ScheduledThreadPoolExecutor.schedule 提交自己。因此，取消某一个已经结束的短 Future 不能代表同一 GIF 后续渲染已经停止。

现有专项规则通过 SafeRunnable 中唯一的 GifDrawable 字段定位所有者，核对公开 start / stop / isRunning / recycle 接口。满足原归属条件后先设置对象级暂停保护，再调用 stop；QQ 的 stop 会取消当前调度 Future、移除相关消息，并保存渲染余量。专项只针对对应 GIF 对象，保留池和其他任务。

仍待验证：stop 的原生余量保存与渲染共享同一 GifInfoHandle 锁。如果原生渲染没有返回，stop 也可能等待该锁。本轮接口核对证明结构兼容，不能证明故障机的卡死渲染已可中断。原生代码没有已验证的可中断路径时，不报告已成功停止。

日志里的 sub_dedicated_t、MSFNewServiceSe 先前没有准确 Java 任务映射，现阶段仍不能只凭名称指定停止接口。新版归属信息用于继续确认真实任务类型；如果它们不走受观察的线程池入口，仍需对应业务或原生证据。

负载与处理规则

本次未改变已约定的触发逻辑：只累计 QQ 在用户勾选核心上的实际 CPU 时间，单核满载为 100%；严格超过合计阈值，并持续达到设定时长后尝试处理。前后台沿用同一阈值和时长，数据无效或前后台未知时暂停处理。

任务处理仍先进行身份、配置、窗口、时效及保护线程复核，再按 GIF 专项 → 标准 Future 协作取消的顺序处理，等待实际结束确认。线程池观察本身不触发停止；没有新增独立单线程阈值，也没有整池关闭、线程强杀或进程重启策略。

安装前后配置文本一致，保留当前手机设置：

cpu=285
duration=3
interval=2
cores=255
action=stop_task

cores=255 表示选择 CPU0—7；当前是 285% / 持续3秒 / 间隔2秒。默认阈值和持续时长仍可在模块设置，不由本次升级重置。
