两种规则如何配合

合计规则所选核心上的QQ合计负载
严格超过合计阈值
连续达到合计持续时长
→ 沿用既有处理
单线程规则该线程在所选核心上的合计负载
严格超过单线程阈值
该线程连续达到自己的时长
→ 默认仅记录，可开启自动处理
共用一个采样窗口 → 合并同一目标 → 复核与去重 → 确认实际结果

举例：单线程长期90%，QQ合计120%，合计阈值200%时，原规则不会触发；新规则可以独立发现。四个线程各60%、合计240%，仍由合计规则覆盖。

两条自动处理规则采用“任意一条满足”。合计已满足自己的阈值和时长时，不会等待单线程更长的时长。两条同时命中同一线程，合并触发原因、只发一次处理请求；不同线程保留各自记录。

设置与默认值

设置行为
CPU0—7核心选择自由勾选，两条规则共用。线程迁移后合计它在全部勾选核心上的实际运行时间，不按最后所在核心猜测。
合计阈值 / 持续时长沿用原配置。单核满载100%，合计可超过100%；前后台同规则。
单线程检测开关新增，默认开启。按PID/TID及启动身份，每个线程分别计时；不监控其他应用。
单线程阈值 / 持续时长初始80% / 10秒，用户可改。范围1—100% / 0—3600秒；严格大于阈值才计时，0秒在首个有效超限窗口触发。初始值用于观察，不是已在故障机验证的最优参数。
单线程处理模式默认“仅记录”，不会因新规则请求停止。可切换“自动处理”，保存后生效；此时需要连续确认对应的同一业务。
统一采样间隔两条规则共用一个间隔，没有每核心独立采样或八套阈值。采样间隔决定检查频率，持续时长按完整有效窗口累计；不能识别窗口内每个瞬间。

任务切换时如何防止误处理

  1. 线程负载计时：由主进程逐窗口统计所选核心的真实线程CPU时间；回落、无效、长间断、线程启动身份变化、配置变化或前后台未知时重置。
  2. 业务归属计时：单线程自动处理启用后，目标进程每个有效超限窗口确认实际业务。普通任务须是覆盖窗口的同一个活动任务；反复提交短任务的GIF须有足够业务CPU证据，并对应同一个GifDrawable对象。
  3. 切换或缺失重置：任务/GIF对象变化、缺窗口或证据不足时，业务计时重新开始。线程负载达时长但业务归属未达时长，只显示未处理及具体原因。
  4. 执行前再次核对：身份、配置、前后台、时效和规则来源确认后，检查原任务/对象仍一致，再进入既有GIF专项或Future协作取消。主线程、系统线程、未知普通Handler/原生任务保持原保护。

连续业务确认采用弱引用和有界状态，逐窗口累计，不需要保存数小时的原始执行记录。每轮最多核对16个高负载目标，按负载优先；控制队列或证据缺失时暂停处理，不推定已确认。

GIF归属仍要求完整窗口的实际业务执行证据；当前执行历史约10秒，过长采样间隔可能导致证据不足。当前2秒间隔符合逐窗口核对方式。

界面与日志

设置页分为“监控范围与合计规则”“单线程持续超限规则”“应用设置”。处理表保留原记录层次，新增“触发：合计 / 单线程 / 合计＋单线程”，展示两套阈值和持续时长，更新状态后仍保留当时规则。

新规则仅记录时，表格显示“仅记录”；开启自动处理后，显示等待、未处理原因或实际确认结果。单线程GIF暂停后的复采使用目标线程的所选核心负载，合计触发继续复采QQ合计；负载回落不单独证明停止因果。

原日志增加THREAD_LIMIT事件以及每次快照里的单线程超限数量、累计时长和模式。持久高负载首次达标后记一次事件，后续快照继续保留累计状态；仍从原明细页导出到Download/QQWatchdog。处理清单不导出，没有另外添加日志模块。
