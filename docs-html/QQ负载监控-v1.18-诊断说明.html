QQ负载监控 v1.18

补充失败诊断，继续使用原来的日志导出按钮。2026-10-01 · versionCode 19

这版解决什么

v1.17 的测试截图没有确认成功停止的任务。原日志记录了超限，却没有目标任务类型和调用栈，无法判断任务捕获遗漏、任务切换和取消接口不支持的具体位置。

v1.18 在原监控日志里新增 [DIAG] 技术记录。这里只补定位能力，尚未完成故障机异常线程的业务停止适配。

故障机下一步

  1. 安装同目录的 QQ负载监控.apk，在模块管理器确认启用、作用域包含 QQ。
  2. 强行停止 QQ 后重新打开；打开桌面模块，启动精确核心采集。
  3. 在 QQ 面板按测试需要设置核心和阈值。只有有效样本严格超限、尝试处理失败时，才会自动添加目标诊断。
  4. 再次出现「无法处理」「任务已变化」「未处理」或「仍在运行」后，在 明细 → 导出日志到下载目录 保存并提供新的 TXT。

文件仍在 Download/QQWatchdog/。无需另一套日志工具，也无需额外操作来采集已映射 Java 线程的调用栈。

新增记录

信息用途
QQ 合计、目标线程自身负载、逐核贡献、所选核心、阈值及前后台区分整体超限与单线程占用，避免将表中合计值当成线程自身负载。
PID/TID、任务类、捕获入口、generation、任务开始与采样窗口的时间差判断实际任务是否被捕获、是否覆盖窗口，以及任务变化的原因。
Java 线程状态及最多24层 Java 调用栈只使用实际线程与 TID 映射；不根据相同线程名猜测目标。栈反映诊断时刻，不能单凭它证明采样窗口内的负载归属。
QQ 版本、系统版本、hook 是否成功及失败原因判断设备/版本差异或控制通道异常。

同一目标身份每分钟最多采集一次栈，每个进程两次栈采集至少间隔3秒；未采集时写明限频。无映射、空栈或读取失败会明确标记。

如何读失败原因

代码含义
NO_ACTIVE_TASK未捕获活动任务。可能是已返回、捕获未覆盖或原生执行；不能直接判定线程类型。
TASK_WINDOW_MISMATCH当前任务晚于窗口开始，保留负载归属保护，不取消这个未确认目标。
CANCEL_NOT_ACCEPTED任务没有受支持的取消接口、使用自定义回调、已变化或拒绝取消；详情会给出原因。
CANCEL_NO_RETURN已发起取消，但任务在确认期内仍未返回。
CONTROL_REJECTED / CONTROL_UNAVAILABLE / CONTROL_TIMEOUT设置、身份、采样时效、队列或目标控制通道问题；未记作处理成功。

支持范围

监控仍仅限 QQ，CPU 0–7 可选，默认合计阈值200%，前后台共用阈值。取消策略沿用 v1.17；标准 FutureTask 协作取消后，观察到任务返回才确认成功。

处理状态表仍保留最近100条，仅在当前 QQ 会话内，不导出清单。失败的技术诊断随已有监控日志导出；不记录聊天正文和任务对象内容。原生用户调用栈尚未采集，普通 Runnable、自定义取消回调和原生任务仍需专用停止接口。
